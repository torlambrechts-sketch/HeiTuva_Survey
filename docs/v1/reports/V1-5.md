## 3. The correction

I told Tor that Q44 would make **the wizard gain a step**: open on the use case, purposes
become step two. **It does not, and the bundle never said it would.** `wizSteps` is four
(`hint-placeholder-count="4"`, `wizIsLast: st.wizStep === 3`) and the use-case chips are a
rail INSIDE step 0, above the purposes (NEW:4195–4197).

Found while building it, corrected in `DECISIONS.md` on both lines — Q44's, which carried
the claim, and Q24's, which carried the same wrong word in «a tab, a chip rail, a wizard
step and pack eyebrows».

**Correcting Q24's clause rather than reporting it as unsatisfied is a judgement worth
checking.** The argument for it: the decision-conformance section quotes clauses verbatim,
so a clause known to be wrong must be fixed at the source or every future report quotes
the error. The argument against: a conformance table that never fails is not evidence of
anything, and I removed its first finding by editing the thing it was measuring against.

Both readings are here because I cannot settle it from inside. What I did do: made the
correction visible in the register itself, dated, with the reason, rather than quietly.

The consequence I attached to the wrong claim held for the right reason — step 0 gained a
rail, so the baseline moved.

## 4. Defects found and fixed

Five. **Four were in the tests or the build process rather than in the application**, which
is the second phase running to say that.

1. **The mapping ran once, in the wrong situation.** `M:0049` backfilled at migration time
   and `seed.sql` inserts the packs AFTERWARDS — migrations run before seeds — so every
   shipped pack came back with a null use case. It has to run twice: on prod the packs
   exist and the migration must map them; on a reset the seed creates them and the seed
   must. Now one function with two callers, idempotent on `use_case is null`, with the
   reason in the function's own comment and the three prior removals named.
2. **A test that leaked exactly the rows it was written to prevent.** Full account in § 5.
3. **A check whose failure taught nothing.** `/org|survey|count|n$|threshold/i` flagged
   `description`, because that word ends in "n". Replaced by named identifiers plus a
   positive control on the exact column set. Paired in the test with V1-3's `prosrc`
   incident, under the cost being avoided: **a check whose failure teaches nothing gets
   switched off.**
4. **A malformed seed row.** Splicing the five packs in duplicated a `sort_order`, and
   `db reset` reported `VALUES lists must all be the same length`. Caught by the reset,
   not by review.
5. **The chip parameter was trusted.** An unknown `?kategori=` filtered every pack out and
   drew an empty grid that reads as a broken library rather than a bad link. Now validated
   against the fixed chips plus the registry's keys.

## 5. The finding of this phase

`use-cases.test.ts` inserts a pack with an unknown `use_case` and expects the foreign key
to refuse it. Cleanup was written after the assertion — which runs only on the path where
the refusal happened, and that is the path where there is nothing to clean.

Under the mutation that DROPS the key — the mutation the test exists to catch — the insert
**succeeded** and left the row. Four `probe-` rows survived the round.

**The symptom is what makes this findable, because the failure never looks like itself:**

> A mutation round leaves litter that reads as a real failure in the restored suite, and
> you diagnose a phantom before finding your own.

The restored suite failed "the mapping is TOTAL over every shipped pack" — true, alarming,
and nothing to do with the code. I re-added the constraint, watched it fail again (the
leftover rows violated it), and only then looked at what was in the table.

**The rule, now standing question 4 in `tests/db/clients.ts`:** a test must clean up after
the outcome it is trying to PREVENT, not only the one it expects. Choose the identifier
BEFORE the insert and register it for teardown immediately. And key teardown on something
the test CHOSE rather than something the database returned — a row that was refused has no
id to remember, and an id-based cleanup silently skips exactly the rows that need it.

## 8. What Tor should look at personally, weakest first

1. **§ 3.** I corrected the clause the conformance table would have failed on. That is
   either the right fix or the section quietly losing its first finding, and I argued both
   sides because I cannot settle it from inside.

2. **The `hr` fallback in `app.map_pack_use_cases()`.** An unmapped pack falls to HR rather

   assertion is what stops the fallback hiding a real gap. The pair is deliberate, but it
   means a pack someone forgets to map lands in HR and looks intentional.

3. **`category` is now invisible to the customer.** The comment says dropping it is a
   decision, and the statutory path is named as its reader. Whether a column that only
   code reads should keep a CHECK constraint at all is a question the comment does not
   answer.

4. **Four of five defects were in the tests, not the application — ANSWERED, so it is not
   re-asked each phase.** Tor's reading, and it is neither of the two I offered: *"that is
   what you get when a phase's application surface is small and its verification surface is
   large. V1-4 and V1-5 added registries, seeds and a tab; the tests around them are more
   code than the features. Defects distribute roughly by volume, and your test work is more
   rigorous than the application work, not less."*

   **THE THING TO WATCH IS NOT THE RATIO. IT IS WHETHER A TEST DEFECT EVER MASKS AN
   APPLICATION DEFECT.** So far every one has done the opposite: the leaked probe rows
   surfaced a real mutation result, the skipped-count caught nine silent skips, the regex
   false positive was caught before it was trusted. **If a test defect is ever found to
   have concealed an application defect, that is the signal** — and it is the only form of
   this observation worth raising again.
