### 1.3 Q20 — the cadence vocabulary, in two migrations on purpose

`app.cadence` gains `biennial` and `custom`. «Hvert år» is the existing `annual`.
`biannual` stays in the enum, unused and undocumented in the UI — an enum value cannot be
dropped without rewriting every row that might hold it, and nothing holds it.

Two migrations, because `ALTER TYPE … ADD VALUE` cannot be followed in the same
transaction by anything that uses the value. Measured on PostgreSQL 17.6 rather than
recalled:

```
begin; alter type public.scratch add value 'b'; select 'b'::public.scratch;
ERROR:  unsafe use of new value "b" of enum type scratch
```

with the exception that makes it easy to disbelieve: a type CREATED in the same
transaction has no such restriction, so the pattern works in a from-scratch script and
fails only when altering a type that is already there.

Per Tor, that constraint is written into `20260907000043_cadence_values.sql`'s own comment
block, headed **"THIS MIGRATION EXISTS SEPARATELY ON PURPOSE. DO NOT MERGE IT INTO 0044."**
Whoever hits it will be reading the migration and seeing what looks like a typo in an
unrelated CASE arm, not reading DECISIONS.md.

### 1.4 Q22 — pause, and what it deliberately does not touch

`schedules.paused_at` (`M:0044:10`). The scheduler skips a paused series **before** the
statement that closes the open round (`M:0044:191`), so the round someone is answering is
untouched. That ordering is asserted directly, because "skipped" evaluated after that
statement would still have closed the round:

```
tests/db/recurrence.test.ts
  ✓ THE POINT: the open round stays open while the series is paused
  ✓ POSITIVE CONTROL: an unpaused schedule DOES run
```

Resume (`app.resume_schedule`, `M:0044:136`) recomputes `next_run_at` as the next future
occurrence of the same weekday at `send_at_local`. Neither of the two easier options:
the stale pre-pause timestamp would fire the instant a holiday pause ended, and
`now() + cadence` would drift a Monday survey to whatever day someone happened to unpause
it. Stop is `active = false`, a separate control rather than a second state of pause,
because it is not reversible from the UI.

## 2. Defects found and fixed in this phase

Six, of which four were found by tests written before the code and two by looking at a
capture. None shipped.

1. **`app.run_due_schedules` re-sent every long cadence weekly.** A four-arm CASE with
   `else interval '7 days'`, and `annual` has been in the enum since `M:0001:20`. Replaced
   by `app.cadence_interval`, one definition, complete over the vocabulary.
2. **My own `schedules_custom_shape` CHECK accepted a half-configured custom cadence.**
   `{every: 3, unit: null, weekday: null}` evaluates `true AND NULL AND NULL` = NULL, and
   a CHECK refuses only on an explicit false. The `is not null` conjuncts are load-bearing
   and the comment says so.
3. **A THIRD copy of the interval CASE, in `send_round`.** Full account in § 6.
4. **The Send screen's Pause/Stopp row was nested inside `cadence !== 'once'`,** so it was
   hidden on exactly the surveys that had something to pause. The status row is about the
   series that EXISTS; the picker is about the next send. They are siblings now.
5. **The picker opened on «Én gang» for a survey already running weekly,** so a re-send
   that changed nothing else would have converted it to a one-off. It now opens on the
   live series, then the pack's default, then «Én gang».
6. **The summary read «Går automatisk tilpasset i 4 runder»,** which says nothing about
   how often anything happens. The bundle uses the INTERVAL there (`cadOf(rec).label`,
   NEW:3265), so a custom cadence now reads «Går automatisk hver 3. uke i 4 runder», from
   the same phrase the editor's own line uses.

`send_round` also gains four defaulted parameters for the custom settings, and is
**dropped before being recreated** — adding defaulted parameters to `create or replace`
makes an OVERLOAD rather than a replacement, and PostgREST then refuses the call as
ambiguous.

## 5. Q50 — which clock a scheduled send runs on

Tor asked for this as a decision line drafted here, with the model chosen rather than the
defect merely named. It is written in full in `docs/v1/04-decisions.md`; this is the
argument.

**The defect.** `schedules.send_at_local` is a bare `time` and this schema models no
timezone at all, so every scheduled send runs on UTC: the hourly sweep computes
`now() + interval`, and V1-3's resume trigger is the first code that reads `send_at_local`
for anything. A Norwegian customer who chooses «09:00» is sent at **10:00 in winter and
11:00 in summer**.

Two properties make this worse than an offset bug. It is **silent** — nothing in the
product says UTC, and «09:00» is displayed back exactly as typed. And it **changes twice a
year with nothing in the product changing**, so it presents as intermittent rather than
systematic: the customer who reports "the pulse used to arrive first thing and now it
comes mid-morning" is describing a correct system behaving as designed. A 90-second pulse
landing mid-morning instead of at the start of the day undoes the engagement argument the
whole cadence feature exists to serve.

**The recommendation: timezone on the ORGANISATION.** `organizations.timezone text not
null default 'Europe/Oslo'` — one column, one backfill, every `next_run_at` computed as
`(date + send_at_local) at time zone o.timezone`.

Two reasons that is right rather than merely cheaper.

1. **A Nordic product's spread is small.** Oslo, Stockholm and Copenhagen share an offset
   all year, so the org column is exact for most customers and at most an hour out for a
   Finnish office — against the two-hour, seasonally-varying error it replaces.

2. **Per-group timezone is not a bigger version of this decision; it is a different
   feature wearing a timezone costume.** A schedule belongs to a survey and a round is ONE
   send at ONE instant, so per-group clocks require the sweep to fan a schedule out into
   per-group runs — which changes what a round IS, and a round is the unit that
   k-anonymity, `get_trends`, the rounds panel and every snapshot are built on. If a
   customer with staff across several countries needs staggered sends, the honest answer
   is per-group ROUNDS, decided on its own terms and priced against what it does to the
   aggregation model. Not a column.

**Scope if confirmed.** Three places compute `next_run_at` — the schedule insert in
`send_round` (`M:0045:181`), the advance in `app.run_due_schedules` (`M:0044:249`), and
`app.resume_schedule` (`M:0044:136`) — and all three must go through one helper, because
a fourth copy is exactly how the interval CASE came to disagree with the enum (§ 6). The
conversion must be `at time zone`, never a stored offset: an offset is right for half the
year, which reproduces the intermittent presentation this decision exists to remove.

**The time control belongs to this decision and to nothing else.** V1-3's custom-cadence
editor uses `<input type="time">`, as the bundle does (NEW:2193), and Chromium renders it
as «09:00 AM» for a viewer whose **browser** locale is en-US — the browser's, not the
operating system's, so it is a setting the user can change and not a fact about their
machine. The stored value is always 24-hour, so this is display only. It is **not worth
fixing on its own**: overriding a native control's locale rendering means building a
custom picker, which is more surface, more responsive work and worse accessibility than
the native element — a real regression bought to remove an AM/PM. If that control is ever
rebuilt it should be because THIS decision made it timezone-aware, at which point the
picker has a second job and earns its cost. One reason to touch it, not two.

**Timing:** V1-6, or sooner if a customer is onboarded first. This is a launch-facing
defect, not a refinement.

## 6. The finding of this phase, and what was done about it

`app.run_due_schedules` had an interval CASE with `else interval '7 days'`. Migration 0044
replaced it with `app.cadence_interval` and its comment said why, in as many words: *"a
second copy of this CASE is how the first one came to disagree with the enum."*

**The second copy was in `send_round`** — eleven lines, same four arms, same
`else interval '7 days'`. So after 0044 the sweep advanced an annual survey by a year
while `send_round` still set its FIRST next run a week out. I found it by building the UI,
not by testing.

The test 0044 shipped with did not catch it, and the reason is the lesson one level up. It
asserts the relation over every cadence in the **vocabulary** — which is the right shape,
and is what caught defect 1 — but it drove **one of the two sites** that compute a next
run. Enumerating the values and sampling the call sites is the same mistake wearing a
different hat.

**The general form, written where the next person will read it** (`tests/db/clients.ts`,
beside the other two standing questions):

> A property that must hold EVERYWHERE must be asserted at every site that can violate it,
> and **the set of sites is DERIVED, NOT REMEMBERED**.

And the note that makes it stick: **0044's comment predicted this and the second copy
survived it anyway.** A comment warning about a class of bug does not go looking for other
instances of the class. Only a query does. If you find yourself writing "and make sure
nobody does this elsewhere" in a comment, that sentence is the specification for a sweep,
not a substitute for one.

**So it is a sweep now — not a new gate.** `tests/invariants/threshold-policy.test.ts`
already derives one set from the catalogue: nothing may still call `app.k_threshold()`. It
now derives a second: nothing but `app.cadence_interval` may do interval arithmetic on a
cadence. One more pattern in a query that already runs, which is the shape Tor allowed.
Proven to bite by restoring the pre-0045 `send_round` — flagged by name — and green again
once restored.

One thing the sweep taught immediately: **`pg_proc.prosrc` is the whole body, comments
included**, so the first version flagged `send_round` for the COMMENT explaining what it
had stopped doing. A sweep that reads prose as code produces exactly the false positive
that gets a check switched off, so comments are stripped before matching and the reason is
written where the query is.
