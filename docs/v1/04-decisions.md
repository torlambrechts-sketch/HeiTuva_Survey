# v1 bundle — decisions for DECISIONS.md (Q18 onward)

Every question the second handoff raises that the register must carry.
Each is written so it can be confirmed or overruled in one line. "DEFAULT" is
the recommended answer the plan in `03-plan.md` assumes; overruling one changes
the plan where the phase text says "per Qnn". Anything the bundle implies but
never states is here as a decision, not an assumption.

**Status.** Q18, Q28, Q30, Q31, Q32, Q34, Q35, Q36, Q37, Q43, Q47 and Q48 are
**CONFIRMED by Tor** (2026-09-06) and are in force — Q48 came out of V1-1 rather
than the bundle. The rest are staged: they are confirmed in batches tied to the phase
where each bites, because a decision taken out of context is taken badly. The
batch order is V1-2 (Q30, Q34, Q35, Q43) → V1-3 (Q19–Q23) →
V1-4 (Q25, Q26, Q27, Q29, Q33, Q42, Q46) → V1-5 (Q24, Q44, Q45) → V1-7 (Q41); Q38, Q39 and Q40 belong to no phase and are confirmed when their
subject arises. **Q49 came out of V1-2** rather than the bundle, like Q48: it
is Q28's own closed exemption list demanding a deliberate act, which is the
rule working rather than a gap in it. **Q50 came out of V1-3** the same way —
building the resume rule was the first time anything read `send_at_local`, and

| Q50 | Which clock a scheduled send runs on | **DRAFT — the choice is the MODEL, not the fact that UTC is wrong.** `schedules.send_at_local` is a bare `time` and this schema models no timezone at all, so every scheduled send runs on UTC: the hourly sweep computes `now() + interval`, and V1-3's resume trigger is the first code that reads `send_at_local` for anything. A Norwegian customer who chooses «09:00» is sent at **10:00 in winter and 11:00 in summer**. Two properties make this worse than an offset bug. It is **silent** — nothing in the product says UTC, and «09:00» is displayed back exactly as typed. And it **changes twice a year with nothing in the product changing**, so it presents as intermittent rather than systematic: the customer who reports "the pulse used to arrive first thing and now it comes mid-morning" is describing a correct system behaving as designed. A 90-second pulse landing mid-morning instead of at the start of the day undoes the engagement argument the whole cadence feature exists to serve. **RECOMMENDATION: timezone on the ORGANISATION** — `organizations.timezone text not null default 'Europe/Oslo'`, one column, one backfill, and every `next_run_at` computed as `(date + send_at_local) at time zone o.timezone`. Two reasons it is right rather than merely cheaper. (1) A Nordic product's spread is small: Oslo, Stockholm and Copenhagen are the same offset all year, so the org column is exact for most customers and at most an hour out for a Finnish office — against the two-hour, seasonally-varying error it replaces. (2) **Per-group timezone is not a bigger version of this decision; it is a different feature wearing a timezone costume.** A schedule belongs to a survey and a round is ONE send at ONE instant, so per-group clocks require the sweep to fan a schedule out into per-group runs — which changes what a round IS, and a round is the unit k-anonymity, `get_trends`, the rounds panel and every snapshot are built on. If a customer with staff across several countries needs staggered sends, the honest answer is per-group ROUNDS, decided on its own terms and priced against what it does to the aggregation model. Not a column. **Scope if confirmed:** three places compute `next_run_at` — the schedule insert in `send_round` (`M:0027:209`), the advance in `app.run_due_schedules`, and `app.resume_schedule` — and all three must go through one helper, because a fourth copy is how the interval CASE came to disagree with the enum (V1-3, `app.cadence_interval`). The conversion must be `at time zone`, never a stored offset: an offset is right for half the year, which reproduces the intermittent presentation this decision exists to remove. **THE TIME CONTROL BELONGS TO THIS DECISION AND TO NOTHING ELSE.** V1-3's custom-cadence editor uses `<input type="time">`, as the bundle does (:2193), and Chromium renders it as «09:00 AM» for a viewer whose **browser** locale is en-US — the browser's, not the operating system's, so it is a setting the user can change and not a fact about their machine. The stored value is always 24-hour, so this is display only. **Not worth fixing on its own:** overriding a native control's locale rendering means building a custom picker, which is more surface, more responsive work and worse accessibility than the native element — a real regression bought to remove an AM/PM. If that control is ever rebuilt it should be because THIS decision made it timezone-aware, at which point the picker has a second job and earns its cost. One reason to touch it, not two. | V1-6, or sooner if a customer is onboarded first — this is a launch-facing defect, not a refinement |
