## 2. Per tranche

### S1 — production truth

**S1's result is not that the worker was fixed. It is that the thing I was asked to do would have
destroyed the queue, and the queue is the evidence.**

The instruction was: inspect the queue, then schedule the worker. Scheduling the consumer is the
whole point of a queue that nothing drains. **Doing it would have spent both invitations on a
missing configuration.**

The mechanism, because it is short and it is the finding. Every provider reported «not configured»
as `{ ok: false, retryable: false }`. `mail-worker.ts` archives every non-retryable failure —
correctly, for the case it was written for, which is a bad address. So the first run of a worker
whose provider had never been set up would have leased both messages, called a provider that
could not send, taken the answer as *permanent*, and dead-lettered them. Not lost with an error:
**archived, quietly, as though the addresses were wrong.** The rationale beside the old behaviour
is right about what it feared — «a queue that never drains» — and wrong about the alternative it
implies: a per-message flag makes a **deployment gap** indistinguishable from a **bad address**,
which is CLAUDE.md's catch-all shape in a different construct. It is also the shape S3 spent its
whole tranche on, one level up: a rule written for the case somebody had in mind rather than for
the state.

**The right shape is to refuse to lease at all.** Configuration is a property of the *process*,
not of a message, so it is checked once at startup, before the queue is read: providers gained
`configured()`, the worker asks it first and exits 1 having leased nothing, and `send()` reports a
gap **retryably** so a message can never be spent on one even if the check is ever bypassed. Two
independent barriers, because the cost of being wrong is somebody's invitations.

The same pass closed the fail-open documented at `INTEGRATION_ARCHITECTURE.md:160` — a two-branch
ternary standing in for a three-case question, so an **unknown channel was delivered as email**.

Proven end to end, not asserted: unconfigured → exit 1, queue 1 before and 1 after; configured →
queue 1 → 0, Mailpit 11 → 12, correct recipient, subject, link and anonymity promise; unknown
channel → archived, zero mail sent; SMS gap → still queued.

**The queue was inspected before anything was drained** — the stop condition — and held exactly
the two expected messages and nothing else. They are still there: `queued = 2`, `read_ct = 0`,
`archived = 0`.

**The rest of S1, which is the part that was merely work.** `ui_messages` reseeded by exact
row-level diff (32 values had drifted, 1 522 were absent) rather than by pushing 355 kB twice; the
five missing template packs, mapped through `app.map_pack_use_cases()` so the mapping stays one
definition with two callers; the `policy_pronoun` rule; the twelve help articles in both
languages, captured from `scripts/seed-help.ts` itself so its ten D114 corrections still had to
match exactly once each.

**And then the credential, which is what stops delivery and nothing more.** Real delivery needs
HeiTuva's own SES identity — `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and a `MAIL_FROM`
verified in eu-north-1 — plus a host to run the worker on. None exists in this environment. The
`AWS_*` variables that *are* set here belong to the sandbox proxy, and sending mail with
infrastructure credentials that are not HeiTuva's is not something I will do. **This is a
credential, not code.** It is listed after the finding above deliberately: the finding is what S1
produced, and the blocker is only the reason the last step is not taken.

### S2 — CI

Seventeen gates, of which four ran. All seventeen now run on every push, across three parallel
jobs: `static` (tsc, `eslint --max-warnings 0`, build), `database` (copy, the whole vitest suite,
policy, attack, load, db lint) and `browser` (roundtrip, hermetic, interaction, i18n, respondent,
send, export, splash, browser, responsive, visual).

Within each job the gates keep `verify:all`'s own order — that order is not arbitrary, since
`verify:hermetic` deliberately does not reset and `verify:roundtrip` writes extra rows on purpose,
so it is the order known to pass.

**OBSERVED GREEN, NOT INFERRED: run 72 on `5513f88`.** All three jobs, all seventeen gates,
`verify:visual` included, 23 minutes 21 seconds wall clock — `static` 2m15s, `database` 4m41s,
`browser` 23m21s, the three in parallel. This is the number S2 was asked to produce, and it took
four runs to get there because the first three each found a real defect: two of mine in the
product and the harness, and one in the CI I had just written.

**What failed on the way, three times, and all three were mine.** The first run failed because I
carried over `supabase start -x …storage-api…` from a job that ran only `tests/invariants`, where
nothing touched Storage — an enumeration of what the *old* job needed, used as the property «what
a gate needs». The second failed on `audience-freeze`'s FK map, which my own M:0090 had made
imprecise; it is described under S3.

**AND THE THIRD IS THE POINT OF THE WHOLE TRANCHE, SO IT IS WORTH STATING PLAINLY: THE FIRST RUN
THAT REACHED THE SIXTEENTH GATE FOUND A DEFECT I HAD SHIPPED IN S3.** `verify:responsive` reported
four blockers — `admin-brukere` and `admin-brukere/invite-duplicate`, at 390px and at 320px,
`scrollWidth 418 > clientWidth`. The cause is the group `<select>` from S3 item 2: three
`flex-none` controls in a non-wrapping row pin the section at 418px whatever the viewport.

Two things about it are worth more than the fix.

**The gate was not new, not written this session, and not weakened.** It has existed since the
responsive work and it had never run on this branch, because it was one of the thirteen. S2's
entire claim is that a gate nobody schedules is not a gate, and the first schedule of it produced
a finding within one run. That is the claim being paid rather than asserted.

**RESPONSIVE.md's own example stopped being true, and it stopped being true by my hand.** The
clause names this exact row as the narrow case — «This is the Brukere case: email + role select +
status fit cleanly» — which is a COUNT of the controls that existed when it was written, not a
property of the row. S3 added a fourth control and the sentence was silently false. This is
CLAUDE.md's «an enumeration mistaken for a property» in a specification rather than in code, and
the reason it survived review is that the comment in `UsersPanel.tsx` quoted the clause back
approvingly while adding the control that broke it.

The fix follows the clause's own overrides rather than its example: the card treatment does not
apply, because both of its constraints point the other way — every control in the row is
consequential (group, role and Deaktiver all change permissions or access, and none may go behind
an overflow menu) and the rows already sit on a card. So the cluster wraps and the two selects
shrink, **below `md` only**; above it they stay `flex-none` children exactly as the bundle draws
them, and `verify:visual` is green on all twelve desktop and mobile comparisons. `verify:responsive`
re-run: **186 of 186 combinations measured, 0 findings, 0 blockers**, with `admin-brukere` at
`scrollWidth=390` and `scrollWidth=320`, `small=0`, `overlaps=0`.

**AND THE RUN AFTER THE FIX FAILED SOMEWHERE ELSE, WHICH IS THE SECOND HALF OF THE SAME LESSON.**
Run 70 — whose only changes were CSS classes and comments — failed at `verify:roundtrip` on
`audit_events (option.change) {"count":0}`. The gate had passed in run 69 and passes locally, and
nothing in the commit touches options, organisations or auditing. The cause is in the probe: it
clicked the switch, slept a fixed `waitForTimeout(800)`, and queried once. That is a bet that a
server action, its audit insert and PostgREST's read all land inside 800ms — true on a quiet
laptop, false on a shared runner. **Absence measured at one instant was being read as absence**,
which is the same error as the paragraph below and as the report's own §6.

Repaired, not re-run: the read polls for the row against a generous deadline and returns the
moment it exists, and the restore click now waits for its audit row too, because a restore that
races is how one gate's timing becomes the next gate's mystery. The assertion is unchanged
character for character — this repairs an existing probe rather than adding a check, the same
category as this session's `verify:copy` repair. CLAUDE.md is explicit that «flake» is not a root
cause, and a re-run would have bought a green without removing the race.

**AND THE SEVENTEENTH GATE, ON THE RUN AFTER THAT, FAILED FOR A THIRD REASON — ALSO MINE, ALSO
THE SAME SHAPE.** With `verify:roundtrip` and `verify:responsive` both green, run 71 reached
`verify:visual` and stopped in two seconds:

    DEPENDENCY MISSING — the visual suite did not run.
      WebKit (the browser behind the "mobile" project, devices['iPhone 13'])

My CI step said `npx playwright install --with-deps chromium`. The visual suite has **two**
Playwright projects and the mobile one is WebKit. So the step installed the browser I had in mind
rather than the browsers the projects use — **the third enumeration-standing-for-a-property in
this tranche alone**, after the `storage-api` exclusion and the responsive row.

What is worth more than the fix is that this failure arrived **legible**. `browsers.setup.ts`
exists precisely so a missing browser cannot present as six failing screenshots with summary lines
like «login screen» and «the new-survey wizard» — its own comment says the danger is that a real
mobile regression then gets waved away as «oh, that's just the browser thing». It stopped the run
once, named WebKit, and printed the command. **A guard written by an earlier phase caught a defect
written by this one, and it cost one line to fix.** That is the argument for this kind of guard
better than anything I could assert about it.

**One thing about the local re-run is worth recording, because it nearly produced a false
finding.** The first local run reported `small = controls` on *every* page and `dashboard`
overflowing to 695 — a catastrophic-looking result that was entirely an artefact: the harness
attached to a `next start` left over from earlier in the session, whose in-memory manifests
pointed at CSS hashes the rebuild had replaced. `ensureServer` has two guards against a stale
reuse (is the build wired to local, are sources newer than the build) and both passed, because
the *build on disk* was fine — it was the *running process* that was old. A third guard is the
obvious thought and it is exactly what CLAUDE.md forbids mid-phase, so it is logged here and not
built. The rule that saved it is the older one: **a result that says everything is broken is a
claim about the measurement first.**

prod stop being the same thing**, and comment text is the half no behavioural test can see. If the
payload is too large, the answer is more calls, not shorter comments.

## 5. What I decided myself, and might be worth reversing

Listed so they are findable rather than buried in nine commit messages.

1. **A group control on the Brukere row that no bundle draws (D129).** Measured across all three
   handoffs: the users row renders the group as *text*, the two «Gruppe» selects are report
   filters, and the prototype's own invite handler assigns the literal string «Uten gruppe» from
   mock state. I chose the minimal consistent option — the same `select` class as the role control
   beside it. If the next handoff draws membership elsewhere, this is one component and one action
   to move. **It also cost a responsive fix**: a fourth control in that row overflowed at 390px and
   320px, and RESPONSIVE.md's narrow-row clause names this row by name with a control count that
   my change made wrong. Both are described under S2.

   9. **The Brukere row's controls wrap below `md`, and the two selects shrink.** Desktop is
   untouched (`md:flex-none`), and the alternative the clause offers — one card per row — is barred
   by its own two overrides here. If you would rather the row lost a control than gained a second
   line on a phone, the group select is the one to move.
2. **A refused section is marked, not dropped.** `compose_report` returns
   `unavailable: true, reason: 'role_leser'` with the content nulled, rather than omitting the
   section. You said «omitted»; I read that as omitting the *content*, because a section that
   vanishes is indistinguishable from one the editor never added. Easy to change to a true drop.
3. **`names_individuals` as a registry column rather than a list in the function.** Makes the rule
   data, at the cost of a column that only migrations write.
4. **The composite for `result_snapshots.round_id`**, which the audit judged non-equivalent. I bound
   it anyway, because «not currently exploitable» is the reasoning this project has been bitten by.
   It costs nothing and it removes the second instance of the shape.
5. **`apply_retention` now reads the toggle**, defaulting to `true` when the key is absent. No
   existing organisation changes behaviour. But it *is* a behaviour change for anyone who switches
   it off — which is what the switch was drawn to do.
6. **The administrator-only rule is NOT applied on INSERT**, only the floor. Creating surveys is
   what a redaktør is for. If you want survey creation to be administrator-only, that is a
   different decision and a one-line change.
7. **`push` now triggers CI on `claude/**`**, so a working branch is proven by its run rather than
   by its YAML.
8. **Five of the six single-column keys into `survey_rounds` were left alone**, with the reasoning
   in `M:0092`: four carry no tenancy columns, so the round *is* their anchor.

## 6. What I would not conclude from this

- **That the audit's 79 MAJORs were 79 things to fix.** Five groups were named, and inside them the
  fixes collapsed into **four migrations' worth of shape**: a rule applied to one road and not the
  state; a column with no writer; a reference that names a tenant without binding it; and a
  document readable from two places, one of which nobody had guarded. Most of the rest of the audit
  is copy that overstates the product, and prose is not fixed by a migration.
- **That production is now verified.** It is *fingerprinted* — the schema matches local byte for
  byte on all eight hashes, and the two functions the ninth check caught were repaired. That is a
  statement about the schema. The invariant suite did **not** run against prod in this session, and
  no user has exercised any of these paths on prod. An apply is not evidence; a comparison is; and
  a comparison of *schema* is not a comparison of *behaviour*.
- **That the mail worker works.** It works *locally, against Mailpit, end to end*. What is proven is
  that the code path delivers and that the failure modes behave. What is unproven is that HeiTuva
  can send mail at all, because nothing in this environment can hold an SES credential.
- **That CI passing means the seventeen gates agree with my laptop.** Run 72 is green on all
  seventeen, `verify:visual` included, so the comparison that was owed has been made and the
  baselines do survive the runner's Chromium. What it does not mean is that the gates now *catch*
  what they are trusted for — the five limitations in `D131` are untouched, and every one of them
  is a gate being exactly right about what it measures and silent about a room it never claimed to
  cover. Four runs were needed to reach green, and three of them found a genuine defect; that is a
  fair estimate of how much a first schedule surfaces, not evidence that the set is now complete.
- **That the gates missed these findings because they are bad.** Every one of the seven in `D131`
  is a gate being exactly right about what it measures and silent about a room it never claimed to
  cover. The one that mattered most this session — `verify:copy` reading the file rather than the
  table — was green *precisely because* it was looking at the half that had been fixed.
