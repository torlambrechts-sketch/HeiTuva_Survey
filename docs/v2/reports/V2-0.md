## 5. DEVIATIONS

- **The fifth nav item moved out of this phase.** The plan had Oppgaver rendering **inert**
  in V2-0. Q26 looks like the authorising precedent — draw the absence rather than hide it —
  but Q26's panel sits in a **picker** and states **its precondition**
  («krever løpende måling»), which is information a person choosing panels can use. A
  top-level nav item is a promise of a destination, and Oppgaver has no honest precondition
  to state, only "kommer". **D73 governs: a surface must not claim a capability the product
  does not have.** Moved whole to V2-4; `docs/v2/03-plan.md` records it.
- **Q53 changed nothing, deliberately.** The property v2's hardening pass achieves is
  already held, by a different and stronger mechanism. Recorded rather than adopted.
  **D90 is not reopened.**
- Defect 9 above is a deviation that exists in the code and not in the log. It is named
  here with an owner rather than fixed out of scope.

| `respondent` (`/s/[token]`) | original body; **v1** for the language chips and peer results | no — but see below |

**Three surfaces the rule did not settle in advance, and how each was decided:**

1. **The marketing legal pages, for a COPY change.** `personvern` and
   `databehandleravtale` are original-governed, and Q55 rewrites text on both. The table
   assigns a **bundle**, which answers "what should this look like" — it does not answer
   "may this phase change words on a screen another bundle governs". **Decided:** governance
   is about *visual* fidelity; a decision of the register (Q55) outranks any bundle's copy,
   because CLAUDE.md already says this file wins on security and the bundle wins on visuals.
   No layout on either page was touched. **This distinction belongs in § 0.3 and is not
   there** — recommended below.

2. **The respondent surface, for Q54.** The table splits it — original body, v1 chips — so
   "which bundle governs the chips" was answerable, but only because Q31 had already named
   them. A surface whose *parts* have different provenance is the shape the table handles
   least well. It cost nothing here because the answer was "already built".

3. **The app shell, on every screen at once.** The table moves the shell to v2 in V2-0, and
   the shell renders inside all 159 captures. So every capture in this phase changed for a
   reason that is *not* about the screen it shows. Nothing was decided wrongly, but a reader
   diffing `admin-valg` will see a changed header and no admin-valg change — worth stating
   before V2-1 rather than after.

**Recommended amendment to § 0.3, for Tor:** add one line saying the table assigns **visual**
governance only, and that a register decision may change copy on any surface regardless of
which bundle governs it. That is what I did; it should not have to be re-derived.
