## 3. FINDINGS — five, and four are the same question asked at different layers

### 3.1 `invitations_reachable_check` said more than it meant

`CHECK (email is not null or phone is not null)`. **What it means** is «an invitation the
product must DELIVER has somewhere to deliver it». **What it says** is «every invitation names
a person». A voucher invitation is never delivered and must carry no address — Tor's second
condition. Restated in `M:0081`; the symptom arrived far from the constraint, as CLAUDE.md's
referential-maintenance rule predicts for exactly this shape one construct over.

### 3.2 A REVOKE THAT WAS CORRECT AND DID NOTHING — D115's second mechanism

`M:0079` and `M:0080` ended with `revoke all on function … from public`, and 5a3 reported
`close_live_session` and `live_cloud` as **anon execute=GRANTED**. `revoke … from public`
revokes the PUBLIC pseudo-role; Supabase's `ALTER DEFAULT PRIVILEGES` grants EXECUTE to `anon`
**in its own name**. A defence working exactly as designed, **on the wrong holder**. Fixed in
`M:0082`. Logged as D115's second mechanism at Tor's instruction, so that entry is not read as
being about exception handlers: *a defence is only as good as the enumeration it was aimed at,
and the only trustworthy enumeration is the catalogue's.*

### 3.3 `run_mode` was built with no writer

The column existed, the Live page read it, the context bar's «Kjør live» rendered on it, and
the demo seed set it — **and no editor could write it.** Every gate was green while the feature
was reachable only from psql. That is the shape D102 and `created_by` both had, and the
question that has now caught it three times is **«who writes this column»**. Fixed:
`setRunMode` and the drawn «Kjøremodus» card (V2:566-575), asserted in test 18 over the source
rather than by clicking.

### 3.4 The guard had to cover the OTHER road

`app.guard_run_mode_anonymous` fires on `run_mode` **and on `anonymity`**. A `before update of
run_mode` trigger alone would have let a survey reach `live` + `named` by setting the mode
first and the anonymity second. Test 16b is that road.

### 3.5 The capture was wrong twice, and the ERROR screenshot said which

The Live route first clicked the row title — a `span`, not a link. The second attempt clicked
the first «Se svar» and landed on **«Pulssjekk utvikling»**, a standard-mode survey, where
«Kjør live» was *correctly absent*. **The failure looked like a missing button and was a wrong
survey.** The ERROR screenshot is what distinguished them: a capture that fails usefully
because it photographs where it actually was. Now uses the manifest's own `pickSurvey`, whose
comment had already written down the reason (`rows are ordered by creation time`).

## 4. Q78 IS OPEN, AND THE BUILD TAKES THE REVERSIBLE SIDE

Until Tor answers, **the counter is hidden below k and the reveal is refused below k.** If he
answers «as drawn», a guard is removed; the other way round would mean a correlation channel had
already shipped. The capture therefore has **one state**, and that is a statement rather than an
omission: `revealed` is not a state this build reaches on the demo seed by design.

**AND THE FLOOR IS A MITIGATION, NOT A PROOF** — in the same terms as Q78's sentence, because
it is the same problem. k answers «how many people are behind this number»; it does not answer
«how many people could have written THIS WORD». In a room of thirty, a word from four people is
above any k the survey carries and still names a handful. `app.live_word_floor()` raises the
cost of that inference; it does not remove it. **A cloud is a weaker guarantee than an average,
and the honest thing is to say which.**

The floor counts **distinct respondents, not occurrences**, and the fixture is the clearest
statement of why: `say('stress stress stress')` is one person and three occurrences. Against an
occurrence floor she clears it alone and **her own word goes onto the wall in a room that knows
who is present** — the failure the floor exists to prevent, arriving through the floor rather
than around it.

## 5. AN HONEST LIMIT, NOT A GAP (QR-2)

`app.guard_invitation_not_suppressed` returns early on a null email, which is exactly a voucher
invitation, so **a person on the Reservasjonsliste who scans the code is not filtered out.**
This is not a defect. A QR path *cannot* honour an objection **because it does not know who it
is speaking to**, and that follows from the anonymity condition rather than weakening it:
knowing enough to suppress and knowing too much to stay anonymous are the same knowledge.

**The duty moves to the presenter, not the system.** She shares a code in a room; someone who
does not want to answer does not scan. That is a valid discharge — an objection to being SENT
things is not a duty to prevent voluntary participation in a meeting one is already in.
Asserted in test 7, both halves, so it is a checked property rather than a comment.
