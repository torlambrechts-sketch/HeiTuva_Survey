## 2. The derivation, and why it is the phase rather than one finding among several

**The plan's structural constraint was «suppression is enforced where a new source cannot
bypass it», and the test that carries it is not a scenario.** A scenario proves that the
recipient sources I know about skip a suppressed address. The catalogue derivation proves
that **no recipient source reaches one, including ones nobody has written yet** — it
enumerates `pg_proc` for every `insert into survey_invitations` and fails on any that does
not consult `app.is_suppressed`.

**THE PLAN'S OWN COUNT IS THE ARGUMENT.** It said `send_round` has «two insertion points
(`M:0052:107` and `:140`)». There are **three**, in **two** functions:

```
select n.nspname||'.'||p.proname from pg_proc p
  join pg_namespace n on n.oid = p.pronamespace
 where n.nspname in ('public','app')
   and p.prosrc ~* 'insert\s+into\s+(public\.)?survey_invitations';
-->  app.run_due_schedules
     public.send_round
```

The third is **`app.run_due_schedules`** (`M:0052:276`), which builds round N+1 by copying
round N's invitation rows verbatim:

```sql
select distinct on (coalesce(email, phone))
       email, phone, channel, name, group_id, lang
  from public.survey_invitations where round_id = v_prev
```

No membership check. No status filter. Nothing. **A person who objects after round 1 is
re-invited by cron — an article 21 obligation broken by a nightly job, from a path no screen
leads to and no scenario test would have thought to visit.** A hand-written list of two
would have passed while missing it. The derivation took it by name, twice: once when the
guard was stripped from that function (mutation 2), and once when a fourth insertion point
that did not exist when the test was written was added (mutation 10):

```
these create invitations without consulting app.is_suppressed: public.send_to_segment_draft
```

That is the difference between a check and a checklist, and it is why this phase's most
important artefact is eleven lines of SQL in a test rather than anything on a screen.

### And why the trigger alone would not have done it

The plan offered «a trigger on `survey_invitations`, **or** a single `app.resolve_recipients`
both loops must go through». Measured, it needs both, for a reason the plan could not have
known.

Each loop does `insert …; perform pgmq.send('mail_outbox', …)`, and the two are independent.
**The worker sends BEFORE it touches `survey_invitations`** — `scripts/mail-worker.ts:120-144`
calls the provider, then UPDATEs `sent_at`, an update that matches zero rows and says
nothing. **So a dropped row would mean no invitation and a delivered email — the one outcome
a suppression test checking that table would call a pass. A test that confirms the duty was
met in exactly the case where it was broken.**

So the trigger **raises** and each loop **skips first**. The skip is not a second guard; it
is what keeps one objection from aborting a whole round. Mutation 3 demonstrated the designed
failure mode rather than merely failing: with the group loop's skip removed, `send_round`
returned `P0001` and the round did not send at all. That is the right failure for an
unguarded source — loud, and never a partial send.

## 4. DEFECTS

*Two found by the verification pass, both fixed. One is mine; the other was mine to expose.*

### 1 — DEFECT, FIXED. The Medlemmer search field's hit area, and the wrong utility for it

`verify:responsive`: **six entries, one cause** — «touch area 200x44 (<44) on `<input>`: Søk i
medlemmer», at both viewports on all three `admin-malgrupper` states. The bundle draws
`padding:11px 14px` at 13px (V2:2577), which paints a 43–44px control.

**The interesting half is which fix is right, and I reached for the wrong one first.**
`touch-44` is the shared overlay utility — and `app/globals.css:105` says in its own comment
that it is for **non-replaced controls**, because `::after` does not render on an `<input>`.
Applying it would have left the measurement exactly where it was while looking fixed.
`touch-44-field` is the variant for replaced elements: it grows the box with a transparent
border and paints through `background-clip: padding-box`, so **the painted control keeps the
bundle's dimensions at every width** — which is what RESPONSIVE.md rule 2 actually asks for.
The rule is about thumbs; the painted size is a token.

### 2 — BLOCKER, FIXED. A screen this phase does not touch, broken by this phase's seed

`resultater` at 320px: `scrollWidth 350`, on three states. **It measured 0 findings two
chains ago.** Nothing in the diff touches Resultater.

Measured rather than guessed, by sorting every element by `right`:

```
SPAN  "Vises ved minst fem svar"  shrink-0 text-[13px] text-mut  right=350  w=153
```

The threshold sentence (Q42) sits in a `flex items-baseline justify-between` row beside the
question text, with `shrink-0` so it cannot be squeezed into three lines at desktop. At 320px
the question shrinks, the sentence does not, and the pair exceeds the viewport. **The defect
is old; what changed is that V2-3b's seed added a survey whose question and gate combination
reaches that row.**

**This is the fixture gap CLAUDE.md names six times over, running in the useful direction for
once**: «the seed reaches only states the current code creates». A new fixture reached a state
the suite had never rendered, and a real responsive defect fell out of it. The fix is
RESPONSIVE.md's own sentence — remove the width constraint and let `flex-wrap` do the work.
`shrink-0` **stays**, and is why the wrap is needed: below `md` the sentence takes its own
line instead of being squeezed.

### 3 — NOT A DEFECT, recorded because it looked like one

The Reservasjonsliste's reason text appeared to run under the «Opphev» button in the desktop
capture. Measured: reason ends at 601, button starts at 613, `scrollWidth === clientWidth` on
both. It was image scaling. Recorded because the phase's own lesson is that a picture is
weaker evidence than it looks — and here the picture was misleading in the *cautious*
direction, which is still misleading.
