## 3. The security-copy sweep

**Tor asked for this as a list inside whichever phase I was already in, not as a phase, and
not as a decision.** *«If most promises hold it is a defect list you handle, and if most do
not, tell me then.»* **Most hold: 102 of 105.** So it is a defect list, it is handled, and
the full account with every command beside its number is **`docs/DEVIATIONS.md` D113**.
Three things belong in this report rather than only there.

**1 · `verify:copy` had a mute of a kind D110's fourth case did not anticipate.** The gate
exists to catch a fixed number where the threshold is variable, and it passed CLEAN over
`admin.pMinResponsesDesc` — *«Standard {k} svar for nye undersøkelser · **aldri under 3** ·
lovpålagte maler har egen terskel»* — for two phases. The floor is **2**
(`surveys_k_threshold_floor`). It was an **over-promise**, the dangerous direction, sitting
one divider above a sibling sentence on the same panel that correctly said «aldri settes
under to».

Two things hid it, and only the second is the familiar shape. The check **reasoned about the
STRING while the claim lived in a CLAUSE** — its premise was *«a string that INTERPOLATES
cannot assert a fixed number»*, which is true of the first clause and says nothing about the
second. **That is this file's own opening lesson turned back on itself:** *THE DERIVATION
MUST DESCRIBE THE PROPERTY, NOT A SYMPTOM OF IT.* «The string interpolates» is a symptom;
the property is per-clause. And the allowlist entry read `'interpolates {k}'` — **a reason
true about one clause and read as true about the string.** D110 warns that an entry without
a reason is where a finding goes to be forgotten; this shows a **partial** reason does the
same job more convincingly, because it survives review.

**The repaired check earned itself on its first run**, which is the argument for repairing
rather than deleting: it immediately surfaced two more entries with the same defect, one of
them stale in the other direction — `admin.orgThresholdNote` was allowed because *«the «tre»
in it is the CHECK floor»* when the floor has been **2 since Q91** and the string itself was
corrected then. Only the reason stayed at three, saying the wrong thing about a string that
was right.

**This is a repair to existing apparatus, not a new gate.** VERIFY.md's seven gates, 5a3,
the census and the allowlist are what exist; nothing was added. A check that structurally
cannot see what it claims to check is a defect in that check, and D110's whole argument is
that fixing it is the response.

**2 · «Summerte tall beholdes» was the bundle's sentence and it was not true.** All three
handoffs draw it under the retention selector (`HeiTuva.dc.html:5602`, v1 `:3951`, legacy
`:3271`). `app.apply_retention` deletes `answers` and `responses` and snapshots nothing
first; aggregates survive only where a `result_snapshots` row already exists, and **34 of
36** seeded surveys with responses have none. Confirmed end to end, not reasoned: ageing one
survey's responses past its retention and running the job left 0 responses, 0 answers, 5
surviving snapshots. CLAUDE.md settles the conflict — *this file wins on security* — and Q55
is the precedent. The copy now says what is true.

**3 · And the reachable paths do not take the snapshot at all.** Three live functions close
a round; `public.close_round` snapshots, `app.close_rounds_with_survey` and
`app.run_due_schedules` do not — and `close_round` has **no UI caller**. `M:0023` added the
snapshot and its header names this exact failure: *«the retention job deletes answers on
schedule, and a trend line loses its earlier points because nothing ever wrote them down»*.
**Two of the three closers bypass the fix, and one is the cron path that creates the
multi-round case in the first place.** Logged for V2-5 rather than patched here, with the
trap written down: `snapshot_results` checks `app.can_edit_survey`, false for the cron role,
so a naive call returns `forbidden` and writes nothing — **a fix that looks applied and is a
no-op**, which is the same mute this section is otherwise about.

### And this phase's third instance of one class

Tor asked for the `weekly_digest` finding in his words, and it belongs here rather than in a
footnote: **a flag with no call site, written into a user-facing promise, while fixing that
exact class of defect.** I dropped Teams from Q71's copy and kept «i det ukentlige
sammendraget». `weekly_digest` is an option row toggled in Administrasjon and nothing sends
it — no digest path in the mail worker, no cron job producing one. Caught by opening the
capture and reading the subtitle, which is the only way that is ever caught.

The sweep then found two more of the same shape by a different route: `close_round`, which
snapshots and which nothing calls; and `snapshot_results`, reachable only through it and
through a scheduler that lacks the rights to use it. **A mechanism that exists in the
schema, is correct, is tested, and has no live caller reads in review exactly like a working
feature** — and the sentence above it is what makes the absence load-bearing. Three
instances in one phase is what makes it a class rather than an incident.

## 4. DEFECTS

### 1 — DEFECT, FIXED. `task_kinds` arrived OPEN, and 5a3 said so

`anon=READS outsider sees 5/5` on a table that did not exist a day earlier. It is the
registry shape — `key text`, `sort_order integer`, no org id, no survey id, no count, the
label held in `messages/*.json` under the key — so it is allowlisted the way `use_cases`,
`brand_accents` and `segment_fields` are, **and CHECKED the same way**: two tests in
`tests/db/tasks.test.ts` assert the column list against the claim, because *a reason in an
allowlist is an assertion, and an assertion nobody checks is a comment*. The second test
asserts the columns are **exactly** `key, sort_order` — data-not-code cuts both ways, and a
Norwegian label in the table would ship a sixth kind untranslatable.

### 2 — DEFECT, FIXED. «Effektvurdert» was reachable with no assessment

**Found by opening the capture, not by a gate.** `oppgaver.default.desktop.png` showed
«Møtefrie torsdager» at Gjennomført offering **«Flytt til Effektvurdert»** beside the teal
prompt to record the assessment. Both, at once. Measured:

    update public.tasks set status='effektvurdert' where id=<gjennomfort task>;
    status        | assessments
    effektvurdert |           0

`M:0062`'s guard tested the assessment **only at `lukket`**. That is the right place for the
compliance outcome — a duty is not discharged until somebody says what the measure achieved
— and **one step too late for the record**. A card sitting at «Effektvurdert» with nothing
in `task_effect_assessments` is CLAUDE.md's *never fabricate data in the UI* one level above
a value: **the STATE is the fabricated datum**, and it is indistinguishable in review from a
real one, which is what that rule says makes it worse than a gap.

`M:0067` moves the requirement one step earlier and **keeps the `lukket` check**, which is
not redundant: it states the statutory rule (V2:5197) at the boundary that matters, and «no
DELETE policy on the assessments table today» is a fact about a migration, not a property of
the table. Three tests, **proven failing before the migration was applied**. The UI hides
the advance button rather than letting it fail — *a UI must not offer an action it knows the
database will refuse*, the same principle that already stops it offering a skip. Confirmed
in the re-captured mobile screenshot: the button is gone from that one card and present on
every other.

### 3 — DEFECT, FIXED. Two 320px blockers, and a green that was measured against stale code

`verify:responsive` reported **2 blockers**: the Oppgaver filter pill's hit areas overlap at
320px, «Alle»/«Lovpålagt» by 369px² and «Mine»/«Lovpålagt» by 225px². The row used
`gap-[3px]`, and RESPONSIVE.md names the floor explicitly — *«a minimum 4px vertical gap
purely for hit-area separation — use the design's existing spacing step at or above that,
never a smaller one»*. Fixed with `gap-x-[3px] gap-y-[13px] … xl:gap-y-[3px]`, which is not
a new value: it is what `ReportsScreen.tsx:94` and `ReportSidePanel.tsx:121` already use for
**this exact control**. The spacing is layout and may change; the chip is a token and may
not.

**The part worth reading is why it was green the run before.** The earlier chain reported
«172 measured, 0 findings, 0 blockers» — against a server the harness had refused to
rebuild. The refusal came one gate later, at `roundtrip`, as *«a server is already running,
but source files are newer than the build it is serving»*; by then `responsive` had already
passed on the old build. **The harness caught the stale server; it caught it at the wrong
gate, so a green was recorded on code that was not the code.** The chain was re-run from
scratch on a killed server, and that run is the one this report cites. It is D110's second
case — a gate that cannot run reporting as though it had — with the twist that it *did* run,
on the wrong thing.

### 4 — NOT A DEFECT, recorded because it looked like one

`builder.lockedNotice` — *«Spørsmålene kan ikke endres nå»* — appeared unenforced during the
sweep: no trigger on `questions`, no status test in `app.can_edit_survey`. Both true, both
irrelevant. **There is no `questions` table.** It is `survey_questions`, and
`sq_freeze_after_send` covers `INSERT OR DELETE OR UPDATE`. Impersonating a real
administrator through the RLS path PostgREST uses, the update raised *«survey … has an open
or closed round; its questions are frozen»*. **Absence in a query I wrote is not absence in
the database** — CLAUDE.md's orientation rule in miniature, and it was caught by probing
instead of concluding.

### The mutation round, and why one line of it is worth the section

**The mutation round caught CLAUDE.md's fifth-rediscovery lesson BEFORE it shipped. That has
not happened before in this project — the note has always been written afterwards, never
paid for itself in advance.** Written the way the note warns against — *«reject any UPDATE
unless an assessment exists»* — the suite fails on test 3 with exactly the symptom the note
describes: `the member can be deleted: expected { code: P0001 } to be null`.
`owner_member_id` is `ON DELETE SET NULL`, so deleting an owning member makes Postgres issue
an UPDATE on the task, and a blanket guard makes that member undeletable — **a broken
erasure path wearing a compliance rule's clothes**, discovered on a test about member
deletion rather than about closing tasks.
